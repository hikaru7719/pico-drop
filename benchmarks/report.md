# React Router / SvelteKit 性能比較結果

2026-10-04の測定。React Routerを比較用アプリに導入し、同一の小規模SSR画面で比較しました。既存frontendはSvelteKitのままです。

この条件ではReact Routerで初期ロードのJavaScript容量と操作可能になるまでの時間が増えました。CPU・回線制限時は約440ms遅くなりました。SSRの初期表示はほぼ同等、進捗更新はほぼ同等、説明ページへの遷移はReact Routerのほうが速い結果です。すべての指標で劣化するわけではありません。

## 条件

- Apple M4 Pro / macOS arm64 / Node v24.20.0 / Chromium 153.0.8010.12。
- React 19.3.0 / React Router 8.4.0、Svelte 5.57.1 / SvelteKit 2.70.3、Vite 8.3.1。
- 各条件・各フレームワーク20回、合計80ロード。進捗更新は各ロード20回。新規コンテキスト、キャッシュ無効、サーバーの事前ウォームアップ、実行順交互。
- 通常条件と、CPU 4倍減速・40msレイテンシ・1.6Mbps制限。viewportは390×844。両方SSR + Node本番サーバー。
- 同じCSS・10枚の写真メタデータ・進捗更新・説明画面。計測中にほかのビルド・テストを並行実行していません。

## 解釈と判断できる範囲

初期JavaScriptの展開後サイズは約4.60倍、同条件gzipでは約3.72倍でした。操作可能状態までの中央値は通常17.7 → 30.8ms、制限時297.2 → 737.7ms（約2.48倍）でした。軽量なアプリで初回アクセスを重視する場合、この初期コストはReact Router導入のトレードオフになります。

両方SSRなので、通常条件のFCP/LCPは16msで一致しました。制限時の中央値の差も8msでした。見えるタイミングと操作可能になるタイミングは分けて評価する必要があります。

マウント後の進捗更新の中央値は約15〜16msで、制限時もほぼ一致しました。次のrequestAnimationFrameまでを測っているためフレーム周期の影響が大きく、細かい処理コストやINPの同等性までは断定できません。10枚表示は中央値の優劣が条件で逆転しており、一般的な操作性能の劣化とは判断しません。

説明画面への遷移はReact Routerが通常11.8ms / 制限時63.5ms、SvelteKitが27.9ms / 79.7msで、今回はReact Routerが速い結果でした。ルート構成・追加チャンク・要求数の影響も含むため、別の画面構成へ一般化はできません。

この結果だけで既存Pico Drop全体の移行後性能を確定することはできません。DropViewの全状態、WebRTC転送、写真デコード・ハッシュ・HEIC処理、Cloudflare Workers、Safari/iPhone実機を計測していません。写真の転送速度についての結論もありません。初期負荷の増加を許容できるかを検討する材料として使ってください。

## 検証と再実行

- 比較用両アプリの本番ビルドと型検査。
- 既存frontend・docsの本番ビルドとbackendのWorkers dry-run。
- 全80ロードでSSR HTML、10枚表示、進捗20、ブラウザ例外なし、documentを維持した画面遷移を確認。
- 既存のVitest 52テスト、既存frontend/backendの型検査、リポジトリのlint・整形検査。
