# 複数写真のWebRTC転送ベンチマーク

実際のChromium DataChannelで、本番の `TransferConnection`・送信処理・受信処理を動かす。指定したGitリビジョンと作業ツリーを同じ条件でビルドし、送信開始から受信側の検証と確認応答までを比較する。

## 再実行

リポジトリのルートで実行する。

```sh
mise exec -- pnpm exec playwright install chromium --only-shell
TRANSFER_BASE_REF=229b582b2608d99f740e6a0c6a3b941da4c7126b BENCH_RUNS=9 TRANSFER_FILES=10 mise run bench:transfer
```

`TRANSFER_BASE_REF` の省略時は `HEAD` と作業ツリーを比較する。コミット後に変更前と比較する場合は、上記のように変更前リビジョンを指定する。`BENCH_RUNS` は既定7回、最低3回。各条件・各実装で1回ウォームアップし、その後は実行順を交互に反転する。計測中はほかのビルド・テスト・ベンチマークを実行しない。

- `TRANSFER_PROFILE=local` または `cpu4` で条件を絞れる。
- `TRANSFER_FILES=1` または `10` で枚数を絞れる。
- 結果は `benchmarks/results/transfer.json` に全サンプル・中央値・p95・環境・比較元コミット・両実装のバンドルSHA-256を保存する。`TRANSFER_RESULT` でルートからの相対出力パスを変更できる。
- 空きポートでローカルHTTPサーバーを起動し、終了時にブラウザ・サーバー・一時ビルドを片付ける。

## 計測条件と限界

送信・受信は独立したブラウザコンテキストで、各回新しいPeerと順序保証付きDataChannelを作る。ICEサーバーは使わず、ローカルの直接接続を利用する。認証・共有リンク・シグナリングAPI・ICE接続確立・写真準備は計測区間に含めない。

写真は32×32のJPEGを5MiBまでパディングしたメモリ上のFileで、1枚または10枚・合計50MiB。末尾の値を画像ごとに変え、全写真の順序・名前・SHA-256一致を毎回確認する。実カメラ画像のデコードやディスク読み込み性能の比較ではない。

`local` はCPU制限なし。`cpu4` は両画面のCDP CPU throttling rateを4にする。ネットワーク帯域・遅延は制限していない。CPU減速はスマートフォン全体やWebCrypto・ネットワーク処理の性能を再現するものではない。

計測区間は送信側のDataChannel openから、受信側が全画像をハッシュ・形式検証し、`verified` が送信側へ戻るまで。受信側の `verified-ack` 処理完了も待って成功を判定する。さらに計測区間外で原本と受信ファイルのハッシュを独立に比較する。

進捗コールバックでは実画面と同じく転送バイト数の更新と60秒の監視タイマーの張り直しを行う。Svelteの描画、写真プレビュー、HEIC変換は含めない。`readMs`・`hashMs`・`drainMs` はラッパーで測った経過時間で、非同期処理を含むため合算してCPU時間とは解釈できない。

この結果はローカルChromiumの転送処理の比較であり、Safari・実機・Wi-Fi/携帯回線・TURN経由の改善率を示さない。新規接続ごとの時間にはばらつきがあるため、個別サンプルではなく中央値とp95を確認する。

## 採用した変更

- チャンク生成を `ArrayBuffer.slice` から `Uint8Array.subarray` に変更し、送信前のJavaScript側のデータコピーを省く。ブラウザ内部のコピーまでなくす変更ではない。
- 送信バッファを256KiB超で待機・128KiB以下で再開から、64KiB超で待機・32KiB以下で再開へ変更する。
- バッファ待ちが必要な場合だけPromiseを作って待ち、各チャンクでの不要な非同期処理を減らす。
- 送受信の進捗通知を50ms間隔にまとめる。最初と最終バイト数は即時通知し、受信確認に使う最終値を保証する。

チャンク上限16KiB、原本データ、順序検証、SHA-256検証、形式検証、確認応答は維持する。写真の読み込み・ハッシュ計算は1枚ずつ行い、先読み用のバッファは追加しない。

## 測定結果

各条件9回で、変更前コミットと作業ツリーを交互に比較する。生データは [transfer.json](../results/transfer.json) に保存する。

### 見送った案

バッファを1MiB・再開512KiBへ増やし、チャンクをビューにした予備案を通常CPU・10枚で3回比較した。中央値は変更前3.810秒に対して3.928秒、p95は4.322秒に対して4.715秒で、改善を確認できなかったためバッファ増量は採用しなかった。この予備案は先読み・進捗間引きを含まない。生データは [transfer-buffer-trial.json](../results/transfer-buffer-trial.json) を参照。

次の1枚を読み込み・SHA-256計算しておく案も試した。初回比較は別のUI検証と重なった可能性があったため取り直したところ、10枚で通常CPUの中央値3.519→3.857秒、CPU減速条件3.783→4.093秒となった。初回の改善幅を再現できず、複数枚で悪化したため先読みは撤回した。生データは [transfer-prefetch-trial.json](../results/transfer-prefetch-trial.json) を参照。この候補はコピー・非同期処理の削減と進捗間引きも含んでおり、個々の変更の効果を単独で測った結果ではない。

### 最終比較

2026-11-04、Linux / Intel Core i5-1135G7 / Node.js 24.20.0 / Chromium 156.0.8078.4で計測。変更前は `229b582`。他のビルド・テストと重ねず、10枚・50MiBを各条件9回ずつ、合計36回と4回のウォームアップで比較した。

時間は秒。各9回のため、今回のp95は各組の最大値に相当する。

| 条件      | 変更前 中央値 / p95 | 変更後 中央値 / p95 | 中央値の変化 |
| --------- | ------------------- | ------------------- | ------------ |
| 通常CPU   | 3.478 / 4.676       | 3.146 / 3.945       | -9.6%        |
| CPU減速×4 | 4.184 / 5.027       | 2.007 / 3.397       | -52.0%       |

通常CPUの中央値が約10%、CPU減速条件が約52%短縮し、今回のp95も両条件で短縮した。ただし新規接続ごとの変動があり、この比率を実機・実回線の改善率とは解釈しない。単枚・少容量は最終候補の測定対象に含めていない。

進捗通知回数の中央値は、通常CPUで送信3,200→21回・受信3,200→26回、CPU減速条件で送信3,200→34回・受信3,200→28回。最終バイト数・全画像のSHA-256一致・確認応答は全36回で成功した。
