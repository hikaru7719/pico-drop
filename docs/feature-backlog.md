# 魅力を高めるための機能バックログ

作成日: 2026-10-18

競合調査と現在の実装を踏まえ、「その場にいる人と、写真を気軽に交換できる」体験を強化するためのタスク。チェックボックスは未完了の作業を示す。優先度・実装負荷・人数などの数値は提案段階であり、確定仕様ではない。

## 現在の実装と前提

- QR・期限付きリンク、原本転送、HEIC/HEIFの任意変換、複数枚の共有保存、同じ写真の再共有は実装済み。
- 送信者はパスキー認証必須、受信者は登録不要。写真はサーバーに保存しない。
- 現在は1リンク1人・1接続1転送、1回10枚・合計50MiB。双方が画面を開いて操作する。
- 受信写真は受信完了から最大10分間、ブラウザ内で一時保持する。共有シートの成功は写真アプリへの保存完了を保証しない。
- HEIC変換は利用者の操作でCloudflareへ送信する。端末内だけで処理する機能とは区別する。
- 実装の詳細は [MVP実装メモ](mvp.md)、[写真処理の設計](photos.md)、[認証方針](auth.md)を参照する。

## 推奨する着手順

1. T01の接続・実機検証、T02の保存体験を整える。T03の計測設計も並行して進める。
2. 目玉機能としてT04の少人数への配布を追加する。
3. T05の送り返し、T06の位置情報除去を進める。
4. 利用状況を見てT07の軽量版、T08の端末ペアリングを検討する。
5. T09の写真収集は、利用場面と認証方針を整理してから着手を判断する。

## T01: 接続と再送の体験を整える

優先度: 高（他機能の土台）。実装負荷: 中。

目的: QRを読み取ってから保存するまで、実際の端末・回線で迷わず完了できるようにする。

- [ ] iPhone Safari・Android・PCの主要な組み合わせで、JPEGと実HEIC/HEIFの転送・保存を検証する。
- [ ] 異なる回線、TURN強制接続、上限付近の枚数・容量で確認する。
- [ ] LINE内ブラウザで確認し、非対応時はSafari / Chromeで開く手順を案内する。
- [ ] 対応環境で転送中の画面スリープを抑止し、終了・中止時に解除する。
- [ ] 画面ロック・バックグラウンド・回線変更による中断を検知し、写真選択を保持した再送導線を整える。

完了条件: 対応端末・ブラウザと検証結果を記録し、成功時の保存と失敗時の再送を実機で確認できる。画面スリープ抑止によってバックグラウンド転送まで保証する表現にしない。途中再開は別途検討とする。

## T02: 保存体験を強化する

優先度: 高（早期改善）。実装負荷: 中。

目的: 全写真の共有保存と個別ダウンロードに加え、必要な写真だけをまとめて保存できるようにする。

- [ ] 受信写真の選択・全選択・選択解除を追加する。
- [ ] 選択した写真だけを共有シートへ渡せるようにする。
- [ ] PCなど共有保存が使えない環境向けに、端末内で生成するZIPの一括ダウンロードを追加する。
- [ ] 原本と変換済みJPEGのどちらを保存するか、ファイル名とともに分かるようにする。
- [ ] 保存キャンセル、同名ファイル、期限切れ、上限付近のメモリ使用量を確認する。

完了条件: iPhoneの共有保存とPCのZIP保存で、選んだ写真を取得できる。キャンセル時は期限内の写真を保持し、期限切れ・破棄時はZIPを含む生成データの参照を解放する。

## T03: 初回利用と転送の課題を計測する

優先度: 高（判断材料）。実装負荷: 小〜中。

目的: 機能追加と入口の改善のどちらを優先すべきか判断できるようにする。

- [ ] 登録開始から初回送信完了までの段階と、完了率の集計方法を定義する。
- [ ] 転送成功率、接続・転送時間、失敗理由、TURN利用率を確認できるようにする。
- [ ] 写真本体・ファイル名・共有リンクの秘密・認証トークンを収集しない計測設計にする。
- [ ] 計測情報の保存期間と集計単位を決める。
- [ ] 初回登録の離脱状況を確認し、説明や認証導線の改善を判断する。

完了条件: 指標の分母・分子が明確で、失敗が起きる段階を把握できる。送信完了と端末への保存完了を混同しない。

設計上の検討: 送信者の登録不要化は現行方針の変更を伴う。計測結果を踏まえて検討する候補であり、このタスクだけで認証必須を撤廃しない。

## T04: 少人数にまとめて写真を配る

優先度: 高（目玉機能）。実装負荷: 大。

目的: 食事や旅行で撮った集合写真を、同じQRから友人全員に渡せるようにする。

- [ ] 「みんなに渡す」から共通QRを表示し、複数人が参加できる配布モードを設計する。
- [ ] 参加者一覧と送信者による相手の確認、受信者ごとの受信承諾を追加する。
- [ ] 参加者ごとの待機・転送中・完了・失敗を表示する。
- [ ] 初期案として最大5人程度・順番に転送する構成を検証し、人数上限を決める。
- [ ] 配布終了、期限切れ、送信者切断時に新しい参加を止める。
- [ ] 途中参加・辞退・個別失敗・再送が、他の参加者に与える影響を定義する。
- [ ] 人数分の送信通信量、TURN利用量、スマートフォンのメモリ負荷を検証する。

完了条件: 複数端末が同じQRから参加し、確認・承諾後に写真を受け取れる。配布終了後は参加できず、写真本体をサーバー保存しない。

設計上の検討: 現在の「1リンク1人・1接続1転送」の変更が必要。既存の1対1共有を維持し、参加者ごとの権限・期限・レート制限を定義する。表示名だけで本人確認済みとは扱わない。

## T05: 受け取った相手へ写真を送り返す

優先度: 高。実装負荷: 中〜大。

目的: 「私が撮った写真もどうぞ」を、その交換の流れで行えるようにする。

- [ ] 受信完了画面に「こちらからも写真を渡す」を追加する。
- [ ] 相手を引き継ぎ、QRを再交換せずに写真選択と送信へ進めるようにする。
- [ ] 返信時も受信者の承諾を必要にする。
- [ ] 未保存の受信写真を失わずに返信へ進む状態遷移を設計する。
- [ ] 相手の離脱・期限切れ時の案内と、通常の共有へ戻る導線を追加する。
- [ ] 返信する人の認証要件と、返信できる相手・回数・期限を決める。

完了条件: 写真を受け取った人が、同じ相手に写真を送り返せる。未保存の写真が意図せず破棄されず、第三者への送信権限へ拡大しない。

設計上の検討: 現行の送信者パスキー必須を維持する案と、その交換中だけ匿名返信を許可する案を比較する。匿名返信は認証方針の変更であり、確定仕様ではない。

## T06: 撮影場所を除いて共有する

優先度: 高。実装負荷: 中〜大。

目的: 写真に含まれる位置情報を、送信前に利用者が選んで除けるようにする。

- [ ] 「原本のまま」「撮影場所を除く」の選択を追加する。
- [ ] JPEGから対応し、位置情報の検出・除去を端末内で行う処理を検討する。
- [ ] 除去対象のメタデータと保証する形式を明確にする。
- [ ] 向き・色・画素寸法・画質への影響を実画像で確認する。
- [ ] 未対応形式や処理失敗を明示し、除去済みと誤表示しない。
- [ ] HEIC/HEIF・PNG・WebPへの対応可否と段階的な拡張を検討する。

完了条件: 対応形式では送信されるファイルから対象の位置情報が除去されたことを検証できる。元ファイルを変更せず、再圧縮や形式変換がある場合は利用者に伝える。

## T07: 原本と軽量版を選べるようにする

優先度: 中。実装負荷: 中。

目的: 回線が遅い場面でも、容量を減らして写真を渡せるようにする。

- [ ] 原本を既定とし、任意で軽量版を選べるようにする。
- [ ] 変換前後の容量と、縮小・画質変更の内容を表示する。
- [ ] 形式ごとの変換場所と対応範囲を決め、HEICを外部処理する場合は送信を明示する。
- [ ] メタデータの扱いをT06と整合させる。
- [ ] 変換中止・失敗・メモリ不足時に原本へ戻れるようにする。

完了条件: 原本は変更されず、利用者が選択した軽量版だけが転送される。写真枚数・容量上限の適用方法を定義し、無断の再圧縮を行わない。

## T08: 自分の端末をペアリングする

優先度: 中。実装負荷: 中〜大。

目的: スマートフォンとPCの間で、毎回QRを読み直す手間を減らす。

- [ ] QRなどで端末を登録し、登録済み端末を送信先として選べるようにする。
- [ ] 端末の表示名変更・解除・失効を追加する。
- [ ] パスキーのアカウント認証と端末のペアリングを区別して設計する。
- [ ] オフライン端末の表示と、双方が画面を開く必要があることを案内する。
- [ ] ペアリング情報の保存先・有効期間・端末紛失時の解除方法を決める。

完了条件: 登録後はQRの再交換なしで接続でき、解除した端末とは再登録なしに接続できない。写真本体の永続保存は追加しない。

## T09: みんなから写真を集める用途を検討する

優先度: 将来候補。実装負荷: 大。

目的: イベントや旅行で、主催者が参加者から写真を受け取れるようにする。

- [ ] 主催者が受信用QRを表示し、参加者が写真を送る利用フローを整理する。
- [ ] 主催者がオンラインの間に受け取る方式で、利用目的を満たせるか確認する。
- [ ] 参加者の送信認証、受信承諾、人数・容量制限、重複写真の扱いを検討する。
- [ ] T04・T05との共通化範囲を決め、採用する場合は実装タスクへ分解する。

完了条件: 利用場面、認証方針、写真保持期間、運用負荷を整理し、実装する範囲を判断できる。

設計上の検討: 後日投稿・オフライン受信・クラウドアルバムは、現在の写真をサーバー保存しない方針から外れる。別のプロダクト判断として扱う。
