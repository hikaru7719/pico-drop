# パスキー認証

送信者はパスキーで登録・ログインします。受信者は匿名セッションのまま共有リンクから参加できます。初回は表示名（ニックネーム可）を入力してパスキーを保存し、次回はアカウント名を入力せず保存済みパスキーを選びます。メールアドレス・パスワードは収集しません。

参考にしたのはVlogアプリsetlogのパスキーを入口にする体験です。[公式ヘルプ](https://setlog.notion.site/setlog-33c7a780f48e80e6bc75f119078f0c0f?pvs=143)を参照しました。setlogのサーバー実装やソースコードは参照していません。署名検証には[SimpleWebAuthn](https://simplewebauthn.dev/docs/packages/server)を使用します。

## 設定

公開前にバックエンドの `AUTH_ORIGIN` をフロントエンドの固定した公開オリジン（例：`https://photos.example.com`、末尾 `/` なし）に設定してください。`backend/wrangler.jsonc` の `vars` に指定するか、バックエンドのディレクトリで `mise exec -- wrangler secret put AUTH_ORIGIN` を実行します。未設定・不一致なら公開環境では認証を拒否します。

ローカルでは `http://localhost:5173` または `http://127.0.0.1:5173` のオリジンを使用できます。任意のホスト名での自動判定は行いません。WebAuthnのRP IDは設定したオリジンのホスト名です。公開ドメインの変更は既存パスキーの利用可否に影響するため、登録を始める前に固定してください。外部の認証プロバイダーや鍵の設定は不要です。

## セッションと権限

- 新規アカウントは256個の認証DO（`auth:00`〜`auth:ff`）に分散します。各DOにアカウント、パスキーの公開鍵・credential ID・署名カウンターを保存します。秘密鍵と生体情報はサーバーに送りません。
- 登録にはdiscoverable credentialを要求し、登録・ログインともuser verificationを必須にします。チャレンジ・オリジン・RP ID・署名を検証します。
- チャレンジは5分有効・1回限り。ブラウザのHttpOnly Cookieに結び付け、検証失敗時も消費します。別タブで認証を始めた場合、同じブラウザの古いチャレンジは無効になります。
- ログインは7日間有効。ランダムなトークンのハッシュだけを保存し、CookieにはHttpOnly・SameSite=Strict・HTTPS時Secureと `__Host-` 接頭辞を設定します。再ログイン時は現在のCookieのセッションを失効させます。
- WebSocketの端末セッションにサーバー側でログインセッションを紐付けます。共有リンク作成のたびにログイン期限・失効・アカウント無効化を確認します。匿名参加者が直接 `create-link` を送っても拒否します。
- ログアウトはサーバーのログインセッションを削除します。作成済みの共有リンク・転送は従来の期限・取り消し操作で終了し、次のリンク作成は拒否します。

## 利用制限

認証の開始・検証をIPごとに10分30リクエスト、共有リンク作成をアカウントごとに24時間30回に制限します。認証の開始と検証はそれぞれ1リクエストです。24時間枠は最初のリンク作成時から数え、端末セッションを作り直してもリセットしません。既存のIP単位の端末セッション発行制限とWebSocketのメッセージ制限も継続します。認証入力は24KBまでです。

アカウントの `disabled` をサーバーの保存レコードでtrueにするとログインと新規送信を拒否します。管理画面・管理APIは今回の範囲に含めません。パスキーだけではアカウントの量産や本人の実在確認は防げません。サービス全体の費用上限や招待制は別の対策です。

## 復旧と検証

この段階ではメール復旧・パスキー追加・アカウント統合を提供しません。保存先の同期や別端末のパスキーを利用できなくなると、同じアカウントへの復旧はできません。新規登録を自動でログイン失敗時の代替にせず、画面で登録とログインを明示的に選びます。

`mise run test` でチャレンジの期限・使い捨て・ブラウザへの紐付け、ログアウト失効、匿名送信の拒否、アカウント無効化、利用制限を検証します。`mise run test:e2e` はChromiumの仮想認証器で実際の登録・ログアウト・再ログイン・署名検証・写真転送を行います。実機Safari/iPhone・Androidのパスワード管理サービスとの組み合わせは公開前に確認してください。

## DO分割と既存データ

新規登録の認証DOはランダムに選び、アカウントID・チャレンジCookie・ログインCookieに `v2.<shard>.` を付けます。認証開始と検証を処理するWorkerが変わっても、Cookieで同じチャレンジ保存先に戻ります。ログイン検証ではチャレンジを原子的に消費してから、WebAuthnのuserHandleでアカウントの認証DOへRPCを送り、署名・userHandle・有効状態を検証します。userHandleやルーティング情報だけでは認証できません。

既存パスキーと既存の7日間ログインは `mvp` DOに残し、旧形式のID・Cookieを旧DOへルーティングします。既存ユーザーの認証負荷は旧DOに残りますが、新規アカウントやWebSocket通信は集中しません。旧DOの削除・名前変更は禁止です。既存アカウント自体の移行は別途必要です。

接続用DOは送信セッションごとの `room:<16桁hex>` です。共有リンク・接続トークン・写真変換トークンの先頭16桁がルームIDで、残り48桁はランダムな秘密です。ルームIDは公開情報であり、全トークンの照合や送受信者の権限検証を省略しません。ログイン失効と送信上限は、リンク作成時にアカウントの認証DOへ問い合わせるため、ルームを作り直しても維持されます。

IP制限は `rate:<IPのSHA-256>` DOで管理し、認証DOやルームを変えてもリセットしません。既存の `HUB` 名前空間と `NearbyHub` クラスを使うため、新しいバインディングやDO migrationは不要です。backend、frontendの順に公開し、両方の更新後に画面を再読み込みしてください。更新前の共有リンク・接続・写真変換権限は引き継がず、作り直しが必要です。

## クラスの責務

Cloudflareに登録するDOクラスは、既存データとDOのIDを維持するため `NearbyHub` のままです。`nearby-hub.ts` の `NearbyHub` はHTTP・RPC・WebSocket・alarmの受付と委譲だけを担当し、実処理を次のクラスに分けています。新しいDO名前空間を作る変更ではないため、今回のクラス分離ではデータ移行は不要です。

| クラス        | ファイル                      | 責務                                                                        |
| ------------- | ----------------------------- | --------------------------------------------------------------------------- |
| `AuthHub`     | `backend/src/auth-hub.ts`     | 認証API・認証RPC・認証データの期限処理。署名検証などは `PasskeyAuth` に委譲 |
| `RoomHub`     | `backend/src/room-hub.ts`     | 端末セッション・WebSocket・共有リンク・グループ転送・写真変換権限           |
| `RateLimiter` | `backend/src/rate-limiter.ts` | IP単位の回数制限と期限処理                                                  |

`RoomHub` は認証データを直接読み書きせず、認証DOへRPCで問い合わせます。入口は `hub:role` に用途を記録し、再起動後のalarmも担当クラスへ渡します。このキーがない既存DOでは従来の期限処理を使い、永続的なアカウントデータを保持します。`index.ts` はWorkerの入口とDOルーティングだけを担当します。
