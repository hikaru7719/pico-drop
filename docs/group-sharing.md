# 少人数にまとめて写真を配る

2026-10-18。T04の初期実装。既存の「写真を渡す」は1対1のまま、「みんなに渡す」を追加する。写真本体はWebRTC DataChannelで送り、サーバーには保存しない。

## 操作と確認

送信者はパスキーでログインし、写真を選んで「みんなに渡す」を押す。同じQR・共有リンクから最大5つの受信セッションが参加できる。送信者は参加者一覧に表示された名前と確認コードを、相手の受信画面と照合して「この相手に渡す」を押す。表示名だけで本人確認済みとは扱わない。

受信者はログイン不要。送信者名・写真の枚数と容量を確認し、「受け取る」を押す。両者の操作がそろうまでSDP・ICEの交換、TURN資格情報の取得、写真転送を許可しない。参加者一覧は送信者にだけ通知し、受信者にはほかの参加者の情報を通知しない。

同時に転送するのは1人。待機中の人の確認・承諾は並行して受け付け、転送枠が空いたら、その時点で条件を満たす参加者のうち参加順で選ぶ。承諾していない人が全員を待たせることはない。転送中もQRを表示し、途中参加できる。

## 上限・期限・例外

| 項目                           | 動作                                                                                                                              |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 人数                           | 1配布につき累計5受信セッション。完了・辞退・切断でも枠を解放しない。6人目は拒否                                                   |
| 写真                           | 共通の10枚・合計50MiBまで。配布中の写真変更は不可                                                                                 |
| 期限                           | 作成から10分。参加・確認・承諾・待機・転送すべてこの期限内                                                                        |
| 配布終了・期限切れ・送信者切断 | 新規参加を拒否し、待機中・転送中の受け渡しも終了。完了済みの受信写真は各画面で最大10分保存可能                                    |
| 辞退・個別中止                 | その人だけ終了し、ほかの人の転送を続ける。同じセッションでの再参加は不可                                                          |
| 転送失敗                       | その人を失敗表示にし、次の人へ進む。写真選択と共通QRを維持                                                                        |
| 再送                           | シグナリング接続が残っている失敗した受信者は同じ画面から2回まで再参加。確認・承諾と確認コードを作り直し、全ファイルを最初から転送 |
| 受信者切断                     | その人だけ終了。再接続は新規セッションなので別枠を使う。上限到達時は新しい配布が必要                                              |
| レート制限                     | 作成・参加合計5回/分/セッション、制御メッセージ240回/分/接続。セッション発行20回/分/IPを維持                                      |
| TURN資格情報                   | 開始済みの転送だけ発行。配布送信者は最大15回/セッション、ほかは従来の10回                                                         |

配布の権限は送信者のセッションとリンクのハッシュ、各転送の送受信セッションに結び付ける。第三者は確認・承諾・中止・完了・シグナリングを操作できない。参加・更新はDurable Objectで直列化し、参加者と転送状態を期限付きストレージに保持する。Hibernation後もメモリ上のキューに依存しない。

## 通信量とメモリ

写真の容量をS、受信者をNとすると、再送なしの送信ペイロードはS×N。初期上限は50MiB×5人＝250MiBで、全員に2回ずつ再送すると最大750MiB。実際の通信量には制御・暗号化などのオーバーヘッドが加わる。TURN経由では同じ写真ペイロードが中継されるため、実際の課金対象量はTURNの集計で測る必要がある。

送信者は同じFileの参照を各転送に使い、参加人数分の写真コピーを作らない。PeerとDataChannelは同時に1組だけで、各転送の終了・失敗時に閉じる。受信側のファイル検証用バッファやプレビュー画像などの追加メモリは従来どおり必要。順次転送だけでメモリ上限を保証するものではない。

## 検証

- ユニットテスト: 両者の確認前の開始禁止、第三者操作拒否、匿名送信拒否、同時参加時の人数制限、完了後の順次開始、個別辞退・失敗・切断、再送回数、配布終了・期限切れ・送信者切断時の全体終了。
- コントローラテスト: 個別完了・失敗後の送信接続とQRの維持、写真変更の禁止、受信承諾後の順番待ちと失敗後の再参加。
- `frontend/src/routes/page.scenario.mjs`: Chromiumの送信画面1つと独立した受信画面5つで、同じQRへの参加、確認・承諾前のPeer未生成、順次転送、全員のJPEG 2枚のSHA-256一致、6人目の拒否、配布終了後の参加拒否を検証。390px幅の画面も確認。従来の1対1共有・保存のテストを含む。
- 実機・回線検証は未完了: iPhone Safari / Android / PCの混在、TURN強制経路での実測、上限の10枚・50MiBを5人に配る場合のスマートフォンのピークメモリ、バッテリー・通信量、バックグラウンド移行を確認する。人数上限5人はこの検証後に見直す。
