# pico-drop — プロダクト方針・MVP設計メモ

更新日: 2026-10-04

用途: Codexへの実装引き継ぎ。会話で確定した方針を優先し、未確定の実装詳細は末尾に分離する。

## 1. プロダクト概要とコンセプト

**短期間の共有リンクで、ブラウザから写真を手軽に渡すサービス。** AirDropのような操作感を目指し、ログインやアプリのインストールを必須にしない。軽く、シンプルで、写真を選び、リンクを共有して送る体験に集中する。

- 名称・リポジトリ名: **pico-drop**。
- タグライン候補: **Share photos with a link.**
- 対象: **写真のみ**。複数枚の送受信と進捗表示に対応する。
- 最優先の対応環境: **iPhone Safari**。他のスマートフォン・PCブラウザとの転送も想定する。
- 両者がサイトを開き、オンラインで操作する。AirDrop固有のBluetooth探索やオフライン通信を再現するものではない。

主なユースケースは、旅行・食事・イベントで撮った写真をその場の友人に渡すこと、異なるOSの端末間で写真を渡すこと、自分のスマートフォンとPC間で写真を移すこと。

## 2. 確定しているスコープ

| 項目         | 方針                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| アカウント   | ログイン必須にせず、匿名端末セッションを発行                                             |
| 相手の発見   | 10分間有効・1人だけ参加できる共有リンク                                                  |
| 相手の確認   | 受信側のAccept必須。承諾すると転送開始                                                   |
| 写真の転送   | WebRTC DataChannelでP2P優先、直接接続できない場合はTURN fallback                         |
| 写真の保存   | サーバーに保存しない。R2・D1・KV・DOストレージへの写真保存は行わない                     |
| iPhoneの保存 | Web Share APIで共有シートを開き、ユーザーが写真アプリへ保存                              |
| 画像形式     | JPEG・HEIC/HEIFなど、iPhoneで選択される写真を考慮                                        |
| MVP対象外    | 動画、一般ファイル、チャット、クラウドアルバム、オフライン相手への送信、ネイティブアプリ |

## 3. 技術スタックと役割

| 技術                       | 役割                                                               |
| -------------------------- | ------------------------------------------------------------------ |
| SvelteKit                  | 写真選択、リンク作成・参加、受信確認、転送進捗、プレビュー、保存UI |
| TypeScript                 | フロント・バックエンド・通信メッセージの型定義                     |
| Cloudflare Workers         | Web配信・API・匿名セッション発行・TURN資格情報の発行窓口           |
| Cloudflare Durable Objects | 短命のリンク、端末間の調停、転送セッション、WebSocket signaling    |
| WebRTC DataChannel         | 写真データを端末間で転送                                           |
| Cloudflare TURN / STUN     | 接続候補の取得と、直接接続できない場合の中継                       |
| Web Share API              | 受信した写真をOSの共有シートに渡す                                 |

**Bunは不要であり、必須技術スタックに含めない。** Node.js・pnpm・Wrangler等のCLIはmiseで管理し、frontendとbackendはpnpmワークスペースで管理する。本番バックエンドはCloudflare Workersのランタイムで動作する。

SvelteKitはUI層として使い、WebRTC・signaling・転送処理は独立したTypeScriptモジュールに分離する。フレームワークの選択だけで写真の転送速度が上がるとは想定しない。

## 4. 全体構成

```text
送信側ブラウザ                          受信側ブラウザ
 SvelteKit UI                            SvelteKit UI
      │                                      │
      └──── HTTPS / WebSocket ────────────────┘
                        │
               Cloudflare Workers
                        │
                  Durable Objects
              ・匿名端末のセッション
              ・共有リンクの発行・参加・失効
              ・送信要求 / Accept / Reject
              ・WebRTC signaling / 転送状態

送信側 ═════ WebRTC DataChannel ═════ 受信側
             P2P直接接続を優先
             接続不可時はCloudflare TURNで中継
```

Durable Objectsは制御情報を扱い、写真本体を保存・中継しない。原本の転送はWebRTCを使う。受信後のHEICプレビュー・JPEG変換は利用者の操作でWorkerのAPIへ送り、Images bindingで処理する。TURN使用時には暗号化された通信が中継サーバーを通るため、「常にサーバーを経由しない」とは表現しない。方針は「写真をサーバー保存しない」。

## 5. 基本ユーザーフロー

1. 送信者が写真を選び、匿名端末セッションと10分間有効な共有リンクを作成する。
2. LINEなどでリンクを共有し、送信者は待機画面を開いたままにする。
3. 受信者がリンクを開くと自動参加し、共有内容を取得する。この時点でリンクを消費するが、写真は転送しない。
4. 最初の受信者の参加時にリンクを使用済みにする。送信元・枚数・合計サイズとAccept / Rejectを表示する。
5. 受信者が2分以内に承諾するとRTC接続・転送を開始する。承諾前に写真本体・SDP・ICEを送らない。
6. 受信者がプレビューを確認し、「写真に保存」から共有シートを開いて保存する。

## 6. 共有リンクと匿名セッション

- 合言葉・位置情報・Nearby探索は使用しない。リンクを持つ人が参加できるため、意図した相手1人に共有する。
- 共有リンクは256bitのランダムトークンをURLのfragmentに含める。通常のページリクエストには含まれず、受信画面の読み込み時に認証済みWebSocket経由で送る。
- DOにはトークンのSHA-256ハッシュをキーに、送信者ID・写真メタデータ・作成から10分の期限を保存する。写真本体は保存しない。
- 参加処理は直列化し、最初の参加でリンクを削除する。辞退後の再利用もできず、新しいリンクを作成する。
- 取り消し・再発行・送信者の切断でもリンクを失効させる。期限を各参加要求で確認し、alarmによる回収前でも期限切れリンクを拒否する。
- リンク期限は参加期限。参加後の受信承諾2分・転送10分・受信写真保持10分は独立した期限として扱う。
- 匿名セッションIDと操作用トークンは分け、表示名を本人認証として使わない。セッショントークンはリンクに含めない。

## 7. 転送・一時データの扱い

- WebSocketでSDP・ICE candidateなどのsignalingを交換し、WebRTC接続を確立する。
- P2Pを優先し、接続できなければCloudflare TURNを利用する。具体的なICE候補設定とfallbackのタイムアウトは実装・実測で確定する。
- 写真をチャンク分割し、DataChannelの送信バッファを制御する。複数枚の転送時もメモリ使用量を抑える。
- ファイルID・名前・MIME type・サイズ・チャンク情報を管理し、全データの受信を確認してから完了にする。
- 拒否・キャンセル・切断・タイムアウトを状態として扱い、失敗時に再試行できるようにする。途中再開の高度な実装は後回しでよい。
- 受信した写真は受信完了から最大10分間ブラウザ内で一時保持する。破棄時にはバッファやObject URLを解放し、サーバーログ・キャッシュにも写真を残さない。
- TURNの管理用秘密鍵をブラウザへ渡さず、Workersから短命のクライアント資格情報を発行する。
- 送信要求とTURN資格情報の発行にはレート制限を設け、無制限な要求や中継利用を防ぐ。

Durable Objectsは写真の保管庫ではなく接続の調整役。WebSocket Hibernationを採用して待機中の課金を抑え、復帰時に必要な短命の接続状態を再構成できる設計にする。[Cloudflare WebSocketドキュメント](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

## 8. iPhone Safari・写真保存・画像形式

- HTTPSで提供し、iPhone Safariの実機検証をMVPの初期から行う。PWA化は段階的な改善とし、インストールは必須にしない。
- 転送中は画面を開いた状態を基本とする。バックグラウンド移行・画面ロック時の継続は保証せず、中断を検出して案内する。
- 受信したBlobを適切な名前・MIME typeのFileとして用意し、`navigator.canShare({ files })`で対応を確認する。
- 「写真に保存」のタップから`navigator.share({ files })`を呼び、iOS共有シートの保存操作へ案内する。写真ライブラリへの自動書き込みは行わない。
- 共有シートの項目や形式対応はOS・ブラウザに依存する。APIの成功を「写真アプリへの保存確認済み」と扱わず、キャンセルや非対応時はプレビュー・個別保存等の代替導線を用意する。[Web Share API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API)、[WebKitの画像保存項目に関する不具合記録](https://bugs.webkit.org/show_bug.cgi?id=255641)
- JPEGから動作を固め、HEIC/HEIFの選択・転送・プレビュー・共有保存を検証する。ファイル選択時にブラウザが形式変換する可能性を考慮し、アプリが受け取ったファイルを基準に扱う。
- 拡張子だけで形式を判断せず、HEICを名前だけJPEGに変更しない。転送できることとプレビューできることは分ける。
- 原則として受け取ったデータをそのまま転送し、無断で再圧縮しない。HEICの任意プレビュー・JPEG変換はWorker＋Images bindingで行い、Cloudflareへの送信と画質・向き・EXIFの扱いを明示する。実装仕様は[写真処理の設計](photos.md)を参照する。元データ転送ではEXIF位置情報も残りうる。

## 9. MVPロードマップ

| 段階          | 実装内容                                                                         | 完了条件                                                       |
| ------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1. 土台       | SvelteKit / TypeScript / Cloudflare構成、匿名session API、DO WebSocket signaling | 2ブラウザが接続し、制御メッセージを交換できる                  |
| 2. 最小転送   | DataChannel接続、Accept / Reject、JPEG 1枚                                       | 承諾後だけ転送でき、受信データが一致する                       |
| 3. 写真体験   | 複数枚、進捗、キャンセル、プレビュー、Web Share API                              | iPhone実機でJPEGを受信し、写真アプリへ保存できる               |
| 4. 共有リンク | 作成・共有・参加・期限切れ・取り消し                                             | 位置情報なしで接続でき、再利用・第三者操作を拒否する           |
| 5. 接続性     | TURN fallback、資格情報・制限、HEIC/HEIF検証                                     | 異なる回線とTURN強制条件で転送でき、形式ごとの対応範囲が分かる |
| 6. 公開準備   | エラー導線、Hibernation、データ破棄、利用量確認                                  | iPhone同士・iPhoneとPCで主要フローを確認し、制限事項を記録する |

Safari検証は最終段階まで待たず、段階2以降で継続する。受信承諾前の送信防止、転送失敗、メモリ上限、共有キャンセルを重点的に確認する。

## 10. Cloudflareの料金感

2026-09-24確認時点のUSD価格。税・ドメイン代等は別途。**小規模MVPは月$0〜5程度から始められる可能性がある**が、ユーザー数だけで費用を保証しない。

| 項目            | 目安                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------- |
| Workers         | Freeは10万リクエスト/日。Paidは最低$5/月から、超過分等は従量課金                                   |
| Durable Objects | Free枠あり。リクエスト・実行時間・ストレージ等が課金要素。Free利用はSQLiteバックエンドを前提に確認 |
| 静的アセット    | Workers Static Assetsへのリクエストは無料。Worker実行を伴う処理は別途考慮                          |
| 直接P2P         | 写真本体のCloudflare中継料金なし。端末側の通信量は発生                                             |
| TURN            | SFU/TURN合算の無料枠1,000GB/月、超過は送出データ$0.05/GB                                           |
| 写真ストレージ  | サーバー保存をしないため、写真保管の費用は発生しない                                               |

料金根拠: [Workers料金](https://developers.cloudflare.com/workers/platform/pricing/)、[Durable Objects料金](https://developers.cloudflare.com/durable-objects/platform/pricing/)、[Realtime料金](https://developers.cloudflare.com/realtime/sfu/pricing/)、[TURN課金対象の説明](https://developers.cloudflare.com/realtime/turn/faq/)。無料枠はこのアプリ専用とは限らず、アカウントの他の利用も考慮する。

概算例: 1転送50MB × 月10万回 = 写真約5,000GB。TURN比率10%なら中継される写真は約500GBで、無料枠内に収まる見込み。実際にはプロトコルのオーバーヘッド・再送・課金対象となる送出量で変わる。TURNの課金対象送出量が月10,000GBなら、無料枠を全て使える場合の超過料金は約$450。Workers / DO費用は別途。

主な監視対象はP2P成功率、TURN送出量、同時接続数、DO実行時間。不要なheartbeatを避け、Hibernationを活かす。

## 11. Codexへの実装指示

このメモの確定方針を守り、まず短い実装計画と主要な未確定点を整理してから、ロードマップの順に動くMVPを作る。認証基盤やDBを増やしすぎず、写真保存サーバーを追加しない。Bunは導入不要。

モジュール分離のたたき台:

```text
frontend/src/lib/webrtc/peer.ts        # 接続・ICE・DataChannel
frontend/src/lib/webrtc/signaling.ts   # WebSocketと制御メッセージ
frontend/src/lib/webrtc/transfer.ts    # チャンク・進捗・完了・キャンセル
frontend/src/lib/photos/               # 形式判定・プレビュー・共有保存
frontend/src/lib/protocol/             # メッセージ型・検証
backend/                     # API・Durable Objects
docs/                        # 設計・開発ドキュメント
```

未確定で、実装時に提案・検証する項目: 最低対応iOS版、写真の枚数・容量上限、セッションTTL、ICEのfallback条件、HEIC非対応端末への案内・変換方針。これらを既に合意済みの数値・仕様として扱わない。
